# Архитектурные решения

## Жизненный цикл точки

`pending` → `published` → `resolved` / `rejected`

- `pending` — прислано ботом, не видно на публичной карте.
- `published` — одобрено модератором, видно на карте **бессрочно**,
  пока статус не сменят вручную.
- `resolved` — проблема устранена, точка остаётся на карте (другим
  цветом), попадает в отчёт для города.
- `rejected` — спам/дубль/не по теме, скрыто, но не удаляется.

Отдельной таблицы "решённых проблем" нет — есть `report_status_history`,
которая через триггер в БД автоматически логирует каждую смену статуса.
Выборка устранённых за период — это представление `v_resolved_log`
(см. `db/schema.sql`).

## Категории

Таблица `categories`, а не enum в коде — новую категорию можно добавить
через админку без деплоя. Стартовый набор: нет пандуса, разбитый
тротуар, перекрыт проезд, прочее.

## Модерация и приватность фото

Модерация — через админ-панель (не через Telegram-канал). Модератор
проверяет фото на приватность (лица, номера) при рассмотрении заявки
вручную, до публикации.

Два кандидата на реализацию админки:
- **Django admin** — почти готово из коробки: списки, фильтры по
  статусу/категории, кнопки-действия, экспорт. Быстрее для MVP.
- **FastAPI + своя админка (React)** — больше контроля над UI, дольше
  в разработке.

## Хранение и раздача фото (OneDrive)

Фото заливаются в OneDrive через Microsoft Graph API. В БД хранится
не прямая ссылка, а `photo_ref` (item id в хранилище) — сама точка не
знает, где физически лежит файл.

Публичная карта получает фото не по прямой ссылке OneDrive, а через
собственный backend-прокси: `GET /media/{report_id}` → backend
запрашивает байты у Graph API и отдаёт их сам. Причины:
- прямые ссылки "поделиться" в OneDrive отдают HTML-превью, а не файл;
- неопубликованные (`pending`) фото никогда не должны быть доступны
  по прямой ссылке;
- при смене хранилища в будущем меняется только один сервис, а не
  все ссылки в базе.

Авторизация к Graph API — delegated OAuth с refresh-токеном,
приложение регистрируется в Azure AD.

## Публичный API / карта

Карта и публичный API работают только с представлением `v_public_map`
(см. `db/schema.sql`) — туда не попадают данные о репортёре, модераторе
и внутренние заметки модерации.

## Обработка фотографий

Снимки приходят разного размера, поэтому нормализуются на входе
(`reports/images.py`), до записи в хранилище:

- поворот по EXIF-ориентации (фото с телефона иначе лежит на боку);
- приведение к RGB/JPEG — PNG, HEIC и прозрачность отсекаются;
- полный вариант: длинная сторона до 1600px, качество 82;
- миниатюра: до 400px, качество 78;
- пересохранение без метаданных — вместе с ними удаляются GPS-координаты
  съёмки, которые иначе попали бы в публичный доступ вместе с файлом.

Оба варианта лежат в хранилище рядом, имя миниатюры выводится из ref по
соглашению `<имя>_thumb.jpg`, поэтому в модели остаётся одно поле.

Где что используется: миниатюра — список админки и подсказки на карте,
полный вариант — карточка заявки и попап на карте. Оригинал, присланный
пользователем, не сохраняется.

Telegram при отправке *фотографией* уже сжимает снимок примерно до 1280px,
так что нормализация чаще срабатывает как страховка. Отправку файлом
(без сжатия) бот не принимает.

## Двуязычность

Интерфейс доступен на русском и узбекском.

**Сайт** использует стандартный механизм Django (gettext). Переводы —
в `locale/uz/LC_MESSAGES/django.po`, компилируются в `.mo` при старте
контейнера, поэтому `.mo` в репозиторий не коммитится. Язык
определяется по заголовку браузера, переключатель в углу карты
сохраняет выбор в cookie на год. Строки для JavaScript передаются
через `json_script`, чтобы переводы жили в одном месте, а не
дублировались в JS.

**Бот** переводы хранит в словаре `reports/bot_texts.py`, а не в
gettext. Причина: aiogram обрабатывает сообщения асинхронно в одном
потоке, а активный язык Django — потоко-локальный. При одновременных
диалогах на разных языках он бы «протекал» между пользователями. Язык
диалога передаётся явно: из поля `Reporter.language` и из состояния FSM.

**Категории** переводятся данными, а не кодом: у модели `Category` есть
поля `label_ru` и `label_uz`, метод `label()` отдаёт нужное по активному
языку и откатывается на русский, если узбекского перевода нет. Значит
новую категорию можно добавить через админку сразу на двух языках, без
правки `.po` и деплоя.

Новый язык добавляется так: строка в `LANGUAGES`, `makemessages -l xx`,
перевод `.po`, колонка в `Category`, ключи в `bot_texts.py`.
